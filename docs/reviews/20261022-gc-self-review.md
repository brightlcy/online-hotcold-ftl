# GC correctness self-review / red-team checklist

This is an implementation-agent self-review, not an independent reviewer. Attack cases exercised: no garbage; live-data erase; insufficient migration space; free space inside victim incorrectly counted; invalid pages copied; duplicate ownership; interrupted preflight; nontermination; nondeterministic ties; overflow of the summed free-space count.

The selector subtracts victim FREE pages from a checked global FREE sum. It chooses only INVALID>0 and feasible migration victims. The controller builds complete destination/payload plans and checks the erase counter before the first mutation. No external callbacks or dynamic allocation occur after programming starts. Each valid victim page has exactly one owner due to private NAND ownership and the verified mapping invariant; each destination is distinct and outside victim. After relocation all original valid pages are invalid and erase cannot reject live data under that invariant. Free pages increase exactly by the initial invalid count. Repeated 1000-write twin replay compares decisions, mapping and erase counts and validates every expected payload.

No unexpected failure found. Remaining limitations: counter-overflow defense unexecuted; memory allocation failure not fault-injected (all such allocations precede mutation); no crash/power-loss recovery; no concurrent observer; no automatic write-triggered/background GC. needs_gc exposes an inclusive reserve threshold and the caller explicitly runs GC. High logical occupancy without reserved space can legitimately produce GcBlocked; no progress guarantee is made for unsafe configurations. No GC differential equivalence with Python has been established. No wear-aware selection or WAF result is claimed.
